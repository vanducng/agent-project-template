# Pull requests, commits and reviews

The rule table in the workspace root `AGENTS.md` lists each rule and the check that enforces it; this page keeps the full text.

- Pull request titles: `<KEY>: <plain summary>` - the Jira key, a colon, then what shipped in plain words, e.g. `PRJ-123: added a retry budget to the export job` (product owner, 2026-10-28). No milestone, no slice, no conventional-commit prefix, no bracket tag. The reader learns what the change is from the title and which feature it belongs to from the branch name. Milestone and slice go in the PR body under a `## Scope` section instead. Commit subjects stay plain conventional commits; the tag and scope convention apply to the PR only.
- Pull request bodies are short and carry evidence (operator, 2026-11-03). In order: what changed and why in one to three lines; the evidence; how it was verified, one line per command with its result; the `## Scope` section. Evidence is a before/after pair for anything that changes behavior: a screenshot pair for what a user sees, a measured pair (counts, values, output, exit code) for data, API, CLI or infra, captured and uploaded the way `vd:ship` `references/before-after.md` describes, never through a public host. Fill the repo's PR template when it has one and add nothing it does not ask for. No file-by-file tour, no restated diff, no design essay; detail a reviewer may need goes in one collapsed `<details>` block or stays in the slice record. Aim for one screen (about 30 lines, images aside). Run `vd:unslop` on title and body. Org and project `AGENTS.md` files name the evidence their repos expect.
- A milestone/slice tag in a PR body names the mission and slice, not an opinion: `Milestone: M<n>, <mission name>`, `Slice: S<n>, <slice name>`, `Mission: <mission>/<slice>`.
- Pull request titles, bodies, commit messages, code comments and review comments never contain claude.ai links: artifact links (`claude.ai/artifact/...`, `claude.ai/code/artifact/...`) or session links (`claude.ai/code/session_...`), including attribution footers. Those pages are private to one account, so a link means nothing to other readers and leaks a private reference. Put the content in the pull request itself, or point to a repository doc. The design copy under the feature's `reports/` stays in this workspace.
- Pull request titles, bodies, commit messages and review comments name no person. Write "the product owner decided" or "per the approved intent", never a name. Decisions and their authors are recorded in the slice `PROGRESS.md`, not in the repo.
- Writer and review seats run `/simplify` (vd:simplify) on the slice's own diff before each push; its refactors go in their own commit, and a reviewer asks for it when a diff carries clutter (product owner, 2026-10-19).
- Docs move with the change (operator, 2026-11-02). Before each push, the writer updates the pages that own the changed behavior, config, endpoint or rollout state (the repo's `docs/`, README, runbooks) in the same pull request. The reviewer treats a page left stating the old behavior as a defect. A finding about stale docs that is raised after merge is fixed in a follow-up pull request from the same worktree.
- Tests earn their CI time. Remove or merge a test when the behavior it pins is gone, or when another test or gate (type check, schema validation, lint, a CI check) already pins the same thing; the PR body names what still covers it. A test that is the only guard of a behavior stays (product owner, 2026-10-19).
- Review comments are resolved during development, not at the end. After every push, fetch the bot and reviewer comments, fix the valid ones in the same pull request, reply on each thread with what changed (or in one line why it does not apply), resolve it, and re-check until the pull request is clean, approved and has no unresolved thread on its exact head. A pull request is ready for merge the moment its work is done.
- Schema changes follow the `dbdesign` skill. A pull request that adds or changes a table or column states the invariants as constraints (primary key, foreign keys with their delete rule, unique keys, NOT NULL, CHECK), names the query each index serves, states the retention or deletion rule for any ledger or log table, updates `docs/database/schema.dbml` with a clean `dbdocs validate`, and says whether the migration is reversible or forward-only. Every table carries `created_at` and `updated_at` (Laravel `timestamps()`); the only exception is a pure link table, named as such in the migration and the DBML note. The reviewer seat treats a schema pull request missing any of these as a defect.

## What the checks enforce

- PR screenshots (`fleet pr-shots`, rules from `vd:ship` `references/before-after.md`): every image sits in a table row, as `<img src="..." width="...">`. A phone shot (its row or alt names 390, phone or mobile) is `width="260"`; every other shot is `width="100%"`. `fleet pr-shots <owner/repo> <pr> --fix` rewrites `![alt](url)` and wrong widths inside table rows; a loose image is only reported.
- `fleet pr-lint` reads the PR title and body only: the form of the title, the opening summary, `## Scope`, the length (a review bot's auto-generated summary block is left out of those three), claude.ai links, people from `contacts.yaml` and other orgs from `orgs/*/org.yaml`. A commit, code comment or review comment is not checked.
