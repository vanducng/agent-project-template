# Messages and deliverables

The rule table in the workspace root `AGENTS.md` lists each rule and the check that enforces it; this page keeps the full text.

- Messages to people are drafted, never sent, until the operator approves the exact text (operator, 2026-10-29). This covers chat (Cliq, Slack, Teams, Google Chat), email, ticket comments and edits, calendar invites, docs shared with people, and any PR or review comment that mentions a person. Show the destination (channel and thread or ticket), the full text and any attachment, then wait for a yes on that text; an edit after the yes needs a new yes. After sending, read the message back and log its link or id in the slice `PROGRESS.md`. Seat-to-seat messages inside a rig, PR bodies, commit messages and replies on bot review threads are not covered.
- Links and mentions in messages (operator, 2026-11-05). A message, ticket comment, PR body or digest that refers to a pull request, issue, ticket, run, document or file uses a hyperlink with short text (`example-repo#123` linked, not typed as plain text). A person the message asks something of, or must be told about, is mentioned with the platform's native mention (Jira `@` mention node, Slack `<@user>`), once, so they get the notification; a person who is only named in passing is not. Use the contact keys in `orgs/<org>/contacts.yaml` to find the account id. A Jira comment is a few short paragraphs with a blank line between them, not one block. This sits beside the draft-and-approve rule above and does not replace it. The exception is a PR title, body or commit message, which name no person (next rule); they keep the links.
- Orgs never cross in deliverables (product owner, 2026-10-26). Records inside this workspace (specs, briefs, reports, notes, progress) may name any org and its research. What a seat delivers for one org never names another org of this workspace (any `orgs/<org>`) or its repos, products, hosts, people, channels, tickets or internal docs: code, comments, config, commits, pull request titles and bodies, issues, reviews, tickets, chat messages, and docs shared with that org. Describe a pattern learned elsewhere by what it does ("apply config on merge"), never by where it came from, and strip the source org when copying from a brief or report into a deliverable.
